01

Introduction

1.1 Purpose of this document

This High-Level Design (HDL) document describes the architecture, functional modules, data model and operating environment of the BiG Event & Ticketing Platform. It is written for review and sign-off before detailed technical work proceeds on any new phase, and as a shared reference for how the system is built and why.

1.2 Purpose of the system

BiG is the operational backbone for running a festival-scale event: selling and tracking tickets, checking attendees in at the gate, allocating tent accommodation, and coordinating the volunteers and departments (Finance, Operations, and others) who run the event on the ground.

1.3 Scope

This document covers the platform as a whole — the production system in current use (referred to as V1) together with the modules delivered since as part of an ongoing V2 programme. It also outlines what is planned next, at the level of intent rather than implementation detail.

1.4 Intended audience

Client stakeholders reviewing platform capability and direction; event operations leads planning how departments will use the system; and technical staff on either side who need a map of the system before going deeper into any one part of it.

02

System Overview

One system, used by everyone from a gate volunteer scanning a wristband to a director reviewing department attendance.

2.1 Business context

Running a festival means coordinating several activities that are easy to plan separately and hard to run separately: who has a valid ticket, who has checked in, where they are staying, and who is on duty to make it all happen. BiG brings these into one system so that box office, admissions, accommodation and department management all read from — and write to — the same source of truth.

2.2 Who uses it

Access is scoped by role (what a person is allowed to do) and department (where they are allowed to do it). Five role tiers cover the organisation:

Full access

Administrator

Configures the platform: events, departments, users and system-wide settings.

Full access

Director

Organisation-wide oversight across every department, without day-to-day configuration duties.

Department-wide

Team Lead

Runs one or more departments: manages volunteers, records attendance, works bookings.

Own record

Volunteer

Operates within their assigned department — check-in duty, own attendance history.

2.3 Core capabilities

  • Ticketing & Box Office — sell, look up and manage bookings for an event, including bulk import of pre-sold orders.
  • Admission — check attendees in at the gate, including on-the-spot registration for walk-ups.
  • Accommodation — allocate and track tent assignments per attendee.
  • Volunteer & Department Management — assign staff to departments, track attendance by shift.
  • Reporting — a live dashboard of ticketing, admission, accommodation and staffing.

Architecture Overview

A conventional three-tier web application: a browser-based app, an API server, and a managed database — each hosted independently.

3.3 Request & data flow

A user's browser downloads the Angular application once from static hosting. From that point on, every action in the app — viewing a dashboard, checking in an attendee, editing a booking — sends a request to the API server, which validates the request, applies the relevant business rules and role checks, and reads or writes the database. The database is never reached directly from the browser.

04

Functional Modules

Six modules cover the platform's day-to-day use, from configuring an event through to running it on the ground.

4.1 Users, Roles & Departments

Administrators create user accounts and organise them into departments (Finance, Operations, and others as needed). Each department has one or more Team Leads and a roster of volunteers. Access to every other module is governed by this structure — a Team Lead's actions are automatically scoped to their own department without needing to be configured per feature.

4.2 Events & Pass Types

An event (e.g. a specific festival edition) is configured with its own set of Pass Types — the categories of ticket and add-on being sold (a festival pass, a tent, merchandise). Every booking, every admission check, and every accommodation allocation is tied back to the active event's Pass Types, so a new event can be stood up without re-building the ticketing rules from scratch.

4.3 Box Office — Bookings, Registration & Admission

Box Office covers the full lifecycle of a ticket: pre-sold orders can be bulk-imported from a spreadsheet, staff can look up a booking and manage every attendee on it, walk-ups can be registered on the spot, and attendees can be checked in at the gate — including by QR scan. A single, shared attendee-actions component is used everywhere an attendee is checked in, allocated a tent, or edited, so behaviour is identical whichever screen staff are working from.

4.4 Tent / Accommodation Allocation

Attendees with a tent pass can be allocated a specific tent at check-in, moved if needed, and vacated when they leave. Allocation is tracked per attendee, so occupancy is always known in real time.

4.5 Volunteer Attendance

Each department can mark and review attendance for its volunteers, by date and by shift — supporting volunteers who move between departments mid-event. Directors and administrators get a cross-department view; Team Leads see their own department; volunteers see their own record.

4.6 Dashboard & Insights

A summary view of ticketing, admission, accommodation and (for administrators) volunteer numbers, refreshed from live data — the first screen most users land on after signing in.

06

Interfaces & Integration

6.1 Web application

The platform is used entirely through a responsive web application — no separate mobile app is required. It works on desktop, tablet and phone, which matters directly for gate and box-office staff who operate from handheld devices.

6.2 API layer

All data operations go through a single REST API, which is the only component that talks to the database. This keeps business rules and access control enforced in one place, regardless of which screen a request comes from.

6.3 Bulk data exchange (Excel import/export)

Pre-sold bookings can be imported in bulk from a spreadsheet — validated row-by-row, with duplicate orders rejected automatically. The current set of bookings can also be exported to a spreadsheet in the same shape, for offline records or as a working backup.

6.4 QR-based check-in

Each booking can be looked up by scanning a QR code, taking gate staff straight to that booking's check-in screen instead of a manual search.

07

Security & Access Control

Access is enforced by both role and department, on every request — not just hidden in the interface.

  • Authentication — sign-in issues a secure, httpOnly session cookie; it cannot be read by page scripts, which mitigates a common class of browser-based attack.
  • Role-based access control — every user has a role (Administrator, Director, Team Lead, Volunteer) and, where relevant, department memberships with a permission tier (Read / Write / Manage).
  • Enforcement at the API — access checks run on the server for every request, so the rules hold even if a user finds a way to alter what the browser displays.
  • Transport security — all traffic is encrypted (HTTPS) in production.
  • Account protection — passwords are stored using industry-standard one-way hashing (never in plain text), with policy requirements on password strength and automated protection against repeated login attempts.
  • Audit trail — key security events (sign-ins, failed attempts, permission changes) are logged for review.

Note — this section deliberately stays at a policy level. Implementation-specific detail (algorithms, thresholds, key handling) is withheld from client-facing documents as standard practice, and is available separately under NDA if required for a formal security audit.

Non-Functional Requirements

Responsiveness

Any device, any screen

Every screen is designed to work on desktop, tablet and phone — critical for gate and box-office staff.

Availability

Cloud-hosted, always on

Frontend and backend are both hosted on managed cloud infrastructure rather than on-premise hardware.

Scalability

Managed database

MongoDB Atlas scales independently of the application tier as event data grows.

Usability

Role-appropriate screens

Each role sees only what's relevant to it, reducing training time for seasonal/volunteer staff.

Maintainability

Modular by design

Events, pass types and departments are configurable data, not hardcoded — new events don't require code changes.

Testability

Automated test coverage

Backend and frontend both carry automated test suites, run before changes are released.

10

Assumptions & Constraints

  • One event is "active" at a time per the platform's event selector; historical events remain in the system as archived records.
  • Departments are organisation-wide, not tied to a specific event — the same Finance or Operations team can operate across multiple events.
  • Internet connectivity is required at point of use (gate, box office) — there is currently no offline mode (a planned Progressive Web App upgrade — see Roadmap — is aimed directly at this constraint).
  • User accounts are provisioned by an Administrator or Director; there is no public self-registration.

Progressive Web App — the biggest planned upgrade to the platform's day-to-day usability. It would let staff "install" BiG on a phone or tablet home screen like a native app (no app-store listing needed), open it with one tap, and keep using core screens — such as gate check-in — for a short stretch even if connectivity drops at the venue. Particularly relevant for box office and gate staff on festival grounds, where signal can be unreliable.
