01

Introduction

1.1 Purpose of this document

This High-Level Design (HDL) document describes the architecture, functional modules, data model and operating environment of the BiG Event & Ticketing Platform. It is written for review and sign-off before detailed technical work proceeds on any new phase, and as a shared reference for how the system is built and why.

1.2 Purpose of the system

BiG is the operational backbone for running a festival-scale event: selling and tracking tickets, admitting attendees at the gate with a wrist band, allocating tent accommodation, mapping the festival ground, running workshops, feeding and housing the crew and guests, and coordinating the volunteers and departments (Finance, Operations, and others) who run the event on the ground.

1.3 Scope

This document covers the platform as a whole — the original system (referred to as V1) together with the modules delivered since as part of an ongoing V2 programme. Every release is first checked in a test environment before wider use. It also outlines what is planned next, at the level of intent rather than implementation detail.

1.4 Intended audience

Client stakeholders reviewing platform capability and direction; event operations leads planning how departments will use the system; and technical staff on either side who need a map of the system before going deeper into any one part of it.

02

System Overview

One system, used by everyone from a gate volunteer scanning a wristband to a director reviewing department attendance.

2.1 Business context

Running a festival means coordinating several activities that are easy to plan separately and hard to run separately: who has a valid ticket, who has been admitted, where they are staying, what is happening where on the ground, who is on duty, and how many plates the kitchen should cook. BiG brings these into one system so that box office, admissions, accommodation, the site map, workshops, hospitality and department management all read from — and write to — the same source of truth.

2.2 Who uses it

Access is scoped by role (what a person is allowed to do) , department (where they are allowed to do it) and any extra access granted to other departments at a Read, Write or Manage tier. Five roles cover the organisation:

Full access

Developer

The platform team. Full access, and not tracked for volunteer attendance.

Full access

Administrator

Configures the platform: events, departments, users and system-wide settings.

Full access

Director

Organisation-wide oversight across every department, without day-to-day configuration duties.

Department-wide

Team Lead

Runs one or more departments: manages volunteers, records attendance, works bookings.

Own department

Volunteer

Operates within their assigned department, plus anything they've been granted — gate duty, workshop doors, the mess desk, own attendance history.

2.3 Core capabilities

  • Ticketing & Box Office — look up and manage bookings for an event, bulk import of pre-sold orders, export, and ticket and custom emails to buyers.
  • Admission — admit attendees at the gate by QR code or search, link each one's wrist band, and register walk-ups on the spot.
  • Accommodation — build the tent inventory and allocate places to tent-pass holders.
  • Venue Map — places, zones, routes and the festival boundary on a street or satellite map, with live status for workshops and the Mess Hall.
  • Workshops — venues, a schedule calendar, pre-registration lists, the door by wrist band, and attendance reports.
  • Hospitality — the kitchen count from attendance, the serving desk, guest meal passes, a daily left-over report, and beds for staff and guests.
  • Volunteer & Department Management — assign staff to departments, track attendance by slot (Morning, Afternoon, Night).
  • Communication — notifications to staff phones, announcements, and a Billboard that keeps every message.
  • Dashboard — headline numbers of ticketing, admission, accommodation and staffing.
03

Architecture Overview

A conventional three-tier web application: a browser-based app, an application server, and a database — each run independently.

3.1 Architecture at a glance

3.2 Building blocks

LayerRole
Web appOne responsive app for desktop, tablet and phone, installable on the home screen, opening without signal and receiving notifications.
Application serverAll business rules, validation and access checks, plus background work such as email sends and timed meal reminders.
DatabaseHolds every platform record.

3.3 Request & data flow

A user's browser downloads the application once from static hosting. From that point on, every action in the app — viewing a dashboard, admitting an attendee, serving a meal — sends a request to the application server, which checks the request, applies the relevant business rules and access checks, and reads or writes the database. The database is never reached directly from the browser. A few screens, such as the Venue Map and the workshop Planner, refresh their live numbers by themselves while open.

04

Functional Modules

Ten modules cover the platform's day-to-day use, from configuring an event through to running it on the ground.

4.1 Users, Roles & Departments

Administrators create user accounts and organise them into departments (Finance, Operations, and others as needed). Each department has one or more Team Leads and a roster of volunteers. Access to every other module is governed by this structure — a Team Lead's actions are automatically scoped to their own department without needing to be configured per feature.

4.2 Events & Pass Types

An event (e.g. a specific festival edition) is configured with its own set of Pass Types — the categories of ticket and add-on being sold (a festival pass, a tent, merchandise). Every booking, every admission check, and every accommodation allocation is tied back to the active event's Pass Types, so a new event can be stood up without re-building the ticketing rules from scratch.

4.3 Box Office — Bookings, Registration & Admission

Box Office covers the full lifecycle of a ticket: pre-sold orders can be bulk-imported from a spreadsheet and exported again, buyers receive a ticket email with a tamper-proof QR code, staff can look up a booking and manage every attendee on it, walk-ups can be registered on the spot, and attendees are admitted at the gate by QR scan or search. Admitting someone links the wrist band they are given; a band belongs to one person, ever, and a lost band can be replaced and is flagged wherever it is scanned. The same attendee actions appear on every screen that shows a booking, so behaviour is identical wherever staff are working.

4.4 Tent / Accommodation Allocation

Admins build each event's numbered tent units per tent pass type. Attendees with a tent pass are allocated a place at the gate and vacated when they leave; moving someone is a vacate followed by a new allocation. Allocation is tracked per attendee, can't overfill a tent, and asks for confirmation before mixing genders, so occupancy is always known in real time.

4.5 Volunteer Attendance

Each department marks and reviews attendance for its people, by date and by slot (Morning, Afternoon, Night) — supporting volunteers who move between departments mid-event. Directors and administrators get a cross-department view; Team Leads see their own department; volunteers see their own department, read-only. Attendance also drives the kitchen's meal counts.

4.6 Venue Map

Each event has its own map of the festival ground on a street or satellite view: places as pins, the festival boundary, zones and routes drawn on the map, and imports from Google Earth or My Maps. Admins can change anything; Team Leads change their own department's items, inside the boundary; everyone can view. Workshop areas show live numbers, and the Mess Hall shows whether it is open.

4.7 Workshops

Venues, workshops and categories are set up once per event, then scheduled on a calendar with warnings that never block. Staff build ordered pre-registration lists with a waitlist, admit people at the door by wrist band or search, and report who attended each session, with an Excel export.

4.8 Hospitality

A separate area for feeding and housing the festival's staff and guests. Each event has a mess plan with meal times. Expected Veg and Non-veg counts come from attendance — Directors, Admins and Developers are always expected, Team Leads and volunteers when marked present — plus guest meal passes. Team Leads are reminded to mark attendance before each count is due. A serving desk identifies people by a personal meal QR code, a staff wrist band or search, and records every decision. A daily report compares what was prepared, asked for and served, and tracks what was left over against a goal. Staff and guest beds are allocated by night, completely separately from participant tents.

4.9 Communication

Admins send announcements to chosen roles and departments; the platform itself sends notifications when emails finish sending, when meals change and when attendance is needed. Notifications reach staff devices even when BiG is closed, people choose what they receive, and every message also waits on each person's Billboard.

4.10 Dashboard

A summary view of ticketing, admission, accommodation and (for administrators) volunteer numbers — the first screen most users land on after signing in.

06

Interfaces & Integration

6.1 Web application

The platform is used entirely through a responsive web application — no app-store app is required. It works on desktop, tablet and phone, and can be added to a home screen to open like an app, which matters directly for gate, workshop and mess staff working from handheld devices.

6.2 API layer

All data operations go through the application server, which is the only component that talks to the database. This keeps business rules and access control enforced in one place, regardless of which screen a request comes from.

6.3 Bulk data exchange (Excel import/export)

Pre-sold bookings can be imported in bulk from a spreadsheet — validated row-by-row, with duplicate orders rejected automatically. The current set of bookings can also be exported to a spreadsheet in the same shape, for offline records or as a working backup.

6.4 QR codes and wrist bands

The phone's camera reads three kinds of code: the booking QR code in each ticket email (checked so altered or made-up codes are refused), the QR code on each wrist band (used at the gate, workshop doors and the mess desk), and each staff member's personal meal QR code or a guest's meal pass at the mess. Each kind is recognised for what it is, so one can never pass as another.

6.5 Email

Ticket and custom emails are sent to buyers through an external email delivery service, in the background, within a daily limit. Delivery results, including bounces, come back from the service and are recorded per email.

6.6 Notifications

Notifications are delivered to staff phones and computers through the standard notification services built into browsers and operating systems. No phone numbers are shared and no chat group is needed.

6.7 Maps

Street and satellite map imagery is loaded from online map services; Directions and Street View open Google Maps. Pins, areas and lines can be imported from Google Earth or My Maps files.

6.8 Spreadsheet exports

Bookings, the Email Report, workshop reports and the daily mess report can each be downloaded as an Excel file.

07

Access Control

Each person sees and does only what their role, department and granted access allow.

  • Roles — Developers, Directors and Administrators have full access. Team Leads manage their own department(s). Volunteers work in their own department.
  • Granted access — anyone can be given Read, Write or Manage access to another department, for example a volunteer helping at the gate.
  • Area teams — Box Office, Workshops and Hospitality are run by their own department's team, plus anyone given access to them.
  • Events — Team Leads and volunteers see active events only; draft and archived events are for administrators.

Note — how the platform protects sign-in and data is deliberately not described in client-facing documents.

08

Non-Functional Requirements

Responsiveness

Any device, any screen

Every screen is designed to work on desktop, tablet and phone — critical for gate and box-office staff.

Availability

Cloud-hosted, always on

The platform runs on cloud services rather than on-site hardware.

Resilience

Opens without signal

The installed app opens and shows what's already loaded when the connection drops; actions that must be exact, such as Admit, wait for a connection.

Safe under pressure

No double allocation

When several staff act on the same booking, tent, bed or band at once, the platform settles it cleanly.

Usability

Role-appropriate screens

Each role sees only what's relevant to it, reducing training time for seasonal/volunteer staff.

Maintainability

Modular by design

Events, pass types and departments are configurable data, not hardcoded — new events don't require code changes.

Testability

Automated test coverage

More than 1,500 automated checks run before every release, which is then tried in a test environment first.

09

Releases

Changes are released in stages and are reviewed and tested before they reach a shared environment. Each release is first tried in a test environment (UAT) before wider use. The installed app picks up a new release by itself and offers a Reload. The web app and the application server are versioned separately; the release history is in the Product Guide.

10

Assumptions & Constraints

  • One event is "active" at a time per the platform's event selector; historical events remain in the system as archived records.
  • Departments are organisation-wide, not tied to a specific event — the same Finance or Operations team can operate across multiple events.
  • A connection is needed to make changes. The installed app opens without signal and shows what's already loaded; keeping recent information on the phone and saving some actions for later is the next planned step.
  • User accounts are provisioned by an Administrator, Director or Developer; there is no public self-registration.
  • Hospitality serves and houses staff and guests only; festival-goers use their passes and participant tents.
  • Wrist bands are QR bands read by phone cameras; one band belongs to one person, ever.
